# 多 Key 提速方案：Key 池多通道调度 + 流程受控并行

> 本文件是本轮"对局丝滑度"优化的**实施依据与验收清单**（风格与 upgrade-plan.md 一致）。
> 目标一句话：**不动游戏语义，把"互不依赖的等待"并行掉，让对局纯等待时间约减半。**
> 状态标记：✅ 已完成 / 🔨 初稿已起草 / ⬜ 未开始。

---

## 0. 硬约束与设计原则（继承 upgrade-plan.md）

| 约束 | 含义 | 对设计的强制要求 |
|---|---|---|
| **单 Key 限流** | 智谱按"并发数"限流（1302=429），且套餐等级决定并发额度（Max>Pro>Lite、动态调整），社区实测有人被压到 1 并发 | **每条通道绑定一个 Key，通道内严格串行**——任何 Key 都不会自己撞自己的限流 |
| **语义串行不可破坏** | 白天发言/狼聊/警上演讲/PK 的先后是游戏信息依赖 | 并行只允许发生在**互不依赖**的调用之间；串行语义由流程 await 链保证，调度器不感知语义 |
| **不改变游戏结果** | 并行不能影响结算、亮票顺序、事件可见性 | 亮票仍按座位序归集；夜晚步骤播报顺序保持固定（防时长推断）；隔离审计照跑 |
| **向后兼容** | 现有用户只有一个 Key | 单 Key = 单通道 = 与现状逐字节等价；不配新配置项也能跑 |
| **可观测** | 提速要有数字背书 | 调度器快照暴露通道状态；改造前后用同一批 mock 对局对比纯等待时长 |

## 1. 调研结论（2026-09）

| # | 结论 | 来源 |
|---|---|---|
| 1 | 智谱 1302 = HTTP 429（达到速率限制/套餐到期）；并发额度与套餐等级挂钩并动态调整 | 官方错误码与速率限制文档 |

## 2. 现状与瓶颈（改造前基线）

调度器现状：单通道 FIFO + 优先级（decision > reflection > lesson > prefetch）+ 老化防饿死。
延迟基线（upgrade-plan.md §1，真实遥测）：`speech` p50 41.5s / p90 213.6s；单次调用 p50 5.0s / p90 49.7s。

三处**语义互不依赖、只因单 Key 被迫串行**的环节（本轮并行化的对象）：

| 环节 | 现状代码位置 | 单次规模 | 并行安全论证 |
|---|---|---|---|
| AI 秘密投票 | `flow.js secretVote`（注释明写"逐个思考…单 Key 防限流"） | 8~11 票 × 5~50s | 票互相保密且互不依赖；结果按座位序归集亮票，与思考顺序无关 |
| 夜晚独立步骤 | `flow.js nightPhase` 按顺序逐步执行 | 夜晚合计 100~250s | 守卫/摄梦人/狼人/预言家/乌鸦只**记录选择**到 `game.night`，结算才相互引用（`resolveNightDeaths` 仍在全部完成后单点执行）；女巫必须等狼刀（依赖狼刀结果），保持串行 |
| 局终复盘 | `api.js generateLessons`（注释"逐个复盘…防限流"） | 11 个 × 5~15s | 互不依赖，只写各自的经验条目 |

不做并行的点（语义依赖）：白天发言链、狼队讨论、警上演讲/PK、白天技能询问（前一个的决斗/自爆会终止流程）。

## 3. 核心设计：Key 池多通道调度器

| 决策 | 内容 |
|---|---|
| 通道模型 | **每 Key 一条通道**，通道内严格串行（单 Key 永不撞限流），通道间并行 |
| 任务分发 | 任务与 Key 无关；调度时取"有效优先级最高任务 + 最闲空闲通道"配对（老化防饿死逻辑不变） |
| Key 下发 | `fn(apiKey)`——任务函数收到所在通道的 Key，llm.js 用它覆盖 `cfg.apiKey` 发请求 |
| 配置 | `apiKey` 字段支持逗号分隔多 Key（`"k1,k2,k3"`）；`parseApiKeys()` 归一化；单 Key=1 通道=现状 |
| 限流隔离 | 某 Key 退避/限流期间只占用自己通道（在途任务内重试），其余通道继续——**全局卡死变局部降速** |
| 配额暂停/恢复 | 语义不变：配额类错误仍按现有暂停机制处理，只是粒度从"全局"变"该 Key 通道" |
| 缩容 | `setKeys` 缩容时多余通道停用（在途任务自然完成），通道编号与统计保留 |
| 兼容 | 不配置多 Key 时 = 单通道，行为与历史版本逐字节等价；`enqueue(fn)` 的 fn 忽略多传的 key 参数 |

## 4. 流程受控并行改造点

| # | 改动 | 文件 | 安全要点 |
|---|---|---|---|
| P1 | AI 秘密投票改为受控并行：AI 票各自发起（经调度器排队），`Promise.all` 收齐后仍按座位序归集亮票；FORCE_ENDED 快速传播 | `flow.js secretVote` | 亮票顺序/票型计算不变；人类投票界面照旧先行挂起 |
| P2 | 夜晚步骤两阶段：①按固定顺序**先播报全部** night_step（含死亡角色步骤的节奏停顿，防时长推断）②互不依赖步骤并行收集，女巫在狼刀后单独执行，最后 `resolveNightDeaths` 单点结算 | `flow.js nightPhase` | 结算逻辑零改动；事件可见性零改动；人类只可能在一个步骤中被询问（一人一身份） |
| P3 | 局终复盘并行：11 个 AI 的 `generateLessons` 并行发起、逐个落库（经验池去重照旧） | `api.js generateLessons` | 单 Key 时调度器自动退化为串行，行为同现状 |
| P4 | 反思与白天技能询问**不改**：反思已是低优先级排队偷跑；技能询问有顺序依赖 | — | — |

## 6. 预期收益（估算）

以 4 个 Key、 upgrade-plan.md 延迟基线（p50 5s / p90 50s）估算：

| 场景 | 现状（单通道） | 4 Key 后 | 备注 |
|---|---|---|---|
| 一次放逐投票（10 票 AI） | 50s~8min（串行） | **≈ /4** | 最常见的长等待 |
| 一个夜晚（独立 5 步 + 狼聊 + 女巫） | 100~250s | **≈ max(狼聊, 女巫, 并行组/4)** | 狼聊与女巫仍串行（语义） |
| 局终复盘 | 1~3min | **≈ /4** | 对局结束后的收尾等待 |
| 白天发言链 | 不变 | 不变 | 语义串行，不可能并行 |
| 限流影响面 | 全局暂停 | 只停该 Key 通道 | 健壮性红利 |

## 7. 验收标准

1. `npm test` 全量回归通过（现有 389 项 + 新增 ≥6 项）
2. 新增测试：①双 Key 双通道并发度实测（两个慢任务重叠执行）；②单 Key 严格串行（并发度=1）；③fn 收到对应通道 Key；④并行投票的票型/亮票顺序与串行一致（同一 mock 种子对比）；⑤夜晚"播报全部 → 行动"顺序断言 + 结算矩阵回归；⑥`parseApiKeys` 边界
3. `npm run eval` 确定性矩阵：同种子胜率/指标 Δ0（并行不改变对局结果）
4. 上帝面板调度器快照可见多通道状态
5. 单 Key 用户无感：不配置多 Key 时所有既有测试不加修改通过

## 8. 风险与合规

| 风险 | 缓解 |
|---|---|
| 多 Key 账号侧限流策略动态变化（如被砍到 1 并发） | 通道内本就严格串行，最坏退化为现状 |
| Coding Plan 条款（自建应用直调不享受套餐额度） | 文档明示，由使用者自行权衡 Key 数量与来源 |
| 并行引入的竞态 | 全部并行点只写各自独立的状态位；隔离审计与 eval 矩阵照跑 |
| 暂停恢复与多通道交互 | 配额暂停粒度改为通道级；恢复接口不变（本轮实现，测试覆盖） |
