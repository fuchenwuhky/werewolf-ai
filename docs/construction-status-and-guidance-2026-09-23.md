**目前是“M1 基础能力已大量落地，M2 功能收口中”，不能记为 M2 验收通过，更不是整套双端 UI 已完成。**

## 2. 立即返修清单

### R01 · P1：双端真人操作缺少 pendingId

**证据：** `src/api.js:1804` 起拒绝真实 pending 中缺少 ID 的提交。桌面 `web/app.js:4377`、`:4532`、`:4548`、`:4623` 和手机 `web/m/m.js:3864` 的提交仅含 `{ token, payload }`；两个 API 包装器也未补 ID。

隔离真实 HTTP 复现：创建 human Mock `adv12` 局，等待 `night_guard`，用合法目标提交：

```text
当前双端同形请求 { token, payload }       → 409 PENDING_ID_REQUIRED
同一任务、同一 payload 补上 pendingId    → 200 { ok: true }
```

**修复要求：**

1. 两端从真实 view.pending 获取 ID，随待操作面板固定保存；所有人类动作入口共用提交逻辑，包括女巫专用按钮。
2. 冻结当前 gameId、令牌、pendingId 和 payload 后再发请求。不能给旧面板的答案临时配上“最新任务”的 ID。
3. 409 时保留原草稿，刷新任务并明确提示；不自动重放到下一个任务，不以关闭后端校验修复。
4. 网络结果不明时先同步状态，避免盲目重发。缺 ID 的 409 与原计划写的 428 存在契约差异，应明确统一，但不能因讨论状态码耽误客户端接线。

**验收：** 必须通过真实桌面/手机页面点击发言、投票、夜间目标与女巫动作；捕获浏览器实际请求，确认 ID 来自当时面板。覆盖旧面板、快速连点、响应丢失、任务切换和刷新。测试不得绕过页面自行补 ID。现有 `scripts/e2e.js` 会自己带 ID，无法证明前端已修复。

### R02 · P1：17–20 字合法昵称档案无法回导

**证据：** `src/api.js:2232` 无条件拼接 `（导入）`。20 字昵称可正常建档、导出、预览，但真正导入返回 400“昵称最长 20 个字符”；17–20 字均受影响，多轮回导会继续累加后缀。

**修复要求：** 原样保留昵称；项目允许重名，身份由新 UUID 区分。如需说明“导入副本”，以界面状态说明展示，不写回昵称，不截断用户原文。

**验收：** 17 字、20 字、重名、含 emoji、多轮“导出→导入→再导出”均成功；昵称和头像/偏好/笔记保持一致，原档案不被覆盖。必须走真实 HTTP，不只测试 transfer 辅助函数。

### R03 · P2：手机玩家中心控件触区不达标

**浏览器实测：** 390×844，当前档案、字号、布局三个 select 均仅 **21px 高**；减少动态效果 checkbox 为 17×17px，四个关联 label 的高度也只有约 **22.39px**，不存在足够大的隐形标签触区。

目标节点：`m-pc-profile-select`、`m-pc-pref-font`、`m-pc-pref-layout`、`m-pc-pref-motion`。独立页面没有获得 `.m-sheet` 中已有的输入控件皮肤，出现灰色浏览器原生小下拉框。

**修复要求：** 提取共享 field/select 控件样式，覆盖独立页和弹层，不能只追加 `.m-sheet` 补丁。select 高度至少 48px；checkbox 图形可以小，但可点击 label 至少 48px 高。保留原生 select 的键盘与无障碍能力，不必为外观重写复杂下拉组件。

**验收：** 320×568、390×844，标准/大字号/紧凑布局均测量真实可点击区域；确认无横向溢出、标签不挤占控件、焦点可见。不能仅断言按钮存在或 CSS 字面量包含 48。

### R04 · P2：历史有数据，但用户无法完整查看

**证据：** 双端历史请求固定 `limit=100`，`hasMore` 只显示“还有更多”，没有下一页（`app.js:1626/1638`、`m.js:1249/1259`）。桌面玩家中心只请求 5 条完成局，没有完整历史入口；手机“全部对局”仍截取 20 条，且这些已结束行缺少历史操作。

**修复要求：**

- 对局列表增加“查看全部”和筛选、分页；复用现有 `offset/limit/hasMore`。
- 事件历史按服务端 `nextAfter` 继续请求，提供可点击的“加载更多”，加载失败可重试且不清空已读内容。
- 以 gameId/seq 去重；切档、关页后迟到请求不得覆盖新页面。
- 不把提高一次性 limit 或删除“还有更多”提示当作修复。

**验收：** 至少 65 条对局、251 条非连续 seq 的公开事件，逐页看到最后一项，无重复和遗漏；中途切档不串数据。读取历史不得启动模型/引擎，不得暴露私人事件。

### R05 · P2：归档规则在前端、后端、测试中互相冲突

**事实区分：** 原计划 §5.2 明确禁止的是“有未结束对局的档案进入回收站”，没有明确禁止仅归档。不能把新增的更严格归档要求冒充原计划原文。

但当前前端 `archiveBlockReason()` 明确禁止有未结束局的档案归档；服务端 `updateProfile()` 没有这个限制；`test/m2-ab-acceptance.test.js:476` 反而断言此时归档必须成功。隔离复现确认后端确实会写入 archivedAt，随后档案对局列表返回 404。这不是数据已被删除，但会使可恢复局暂时从常用入口消失。

**建议统一为当前前端已经向用户承诺的保守规则：** 有未结束局时不归档，并保留原有不可进入回收站规则。把最终判断放在服务端；归档与建局/开始之间需要同一档案级串行边界，覆盖内存及磁盘未结束局，不能只在前端预检。

如产品选择允许归档，则必须同步取消前端禁令、提供明确恢复入口，并证明归档后未结束局仍可找回；不能维持三套矛盾定义。实施前在契约文件登记选定方案，再修改对应测试，不得为绿灯随意改断言。

### R06 · P2：昵称计数与开局输入约束不一致

`web/shared/profile-state.js:99` 按 Unicode 码点计数；`src/profiles/store.js:49` 按 UTF-16 长度计数，11 个“🐺”即被后端拒绝。两端开局输入仍为 `maxlength=12`（`web/index.html:213`、`web/m/index.html:193`），档案上限却是 20。

建议统一采用现有共享模型的 20 码点口径，同步服务端、前端、计数提示、导入和开局昵称。原生 maxlength 按 UTF-16 计数，不能简单把属性改成 20 就宣称完成。简介也统一既有 100 字符的实际计数规则。完整昵称存储不截断，只在列表做可展开省略。

验收覆盖中文、英文、emoji、组合字符和粘贴超长输入，验证存储值与显示提示一致。

### R07 · P2：头像校验存在已复现的坏图漏检

`src/profiles/avatar.js:135–160` 检查解压长度，但没有逐行验证滤波字节。CRC 正确、512×512、解压长度正确、第一行滤波值为 255 的 PNG 仍被接受。正常裁切器通常不会生成这种图片，但直接上传或导入包可触发。

在替换旧头像前验证每行滤波类型为 0–4；补合法 1–4 和非法 5/255 的反例，确保失败后原图、元数据及导出不变。不要仅重新计算 CRC。

**另一个已知稳定性风险：** `store.js:327` 承认覆盖 avatar.png 与更新 profile.json 之间强杀会失去内存中的旧图。普通异常回滚测试不等于崩溃原子性。列入 M5 头像持久恢复：临时恢复记录或版本文件机制，启动对账后再清理旧图；不是本次已实测强杀成功的结论。

## 3. UI 下一批怎么做

以下由本次实际页面视觉检查形成，按 frontend-design 的信息层级与一致性原则收敛；不是要求继续堆装饰。保留原计划的骨白、墨蓝、古金和暗红语义，不另起一套风格。

### 3.1 先精修玩家中心，不重写数据层

桌面当前是长弹窗：同一档案先展示一次资料卡，再展示一次带“选用/编辑/战绩/归档/导出”的列表行；说明先于主要信息，用户还要向下滚动才能找偏好与数据管理。手机虽已有独立页面，但统计是一整段小字，控件样式不一致。

| 区域 | 明确实施规格 |
| --- | --- |
| 桌面整体 | 优先独立内容页或宽面板；内容最大宽度约 1120px，24px 内边距、16px 区块间距；以四个分区导航定位资料/战绩/偏好/数据，避免整张长表单塞进窄弹窗 |
| 当前身份 | 桌面头像 80px、手机 64px；昵称为主要文字；仅保留“编辑资料”“切换档案”两个高频动作；重复的当前档案行移出主视图 |
| 档案切换 | 单独列表/抽屉，每行头像、昵称、当前状态、选用；编辑/归档/导出放次级菜单；不让 5 个按钮把昵称挤成竖排 |
| 战绩 | 正式局、胜率、胜/负/平分清主次；试玩/观战/终止作为辅助分桶；分母解释放帮助说明，不显示程序式长句 |
| 数据管理 | 导入/导出为普通操作；归档/回收站在次级区；恢复记录仅有异常时突出提示；UUID、revision 等内部术语不占首页正文 |
| 手机 | 保留四组，但采用一致的行控件和卡片节奏；主要操作高 52px、普通触区至少 48px；数据管理可折叠，但入口名称和状态始终可见 |

桌面普通按钮至少 40px，主要按钮至少 44px。不能为了“紧凑”缩小触区、把整页字号降至 12px，或靠一连串 !important 覆盖旧样式。

### 3.2 再做 M3：首页与真正三步开局

1. 首页只有品牌、当前玩家、继续上局、开始新局三个主要信息层级。去掉重复的配置标签＋同内容长句；API 长表单留在设置。
2. 手机“开始/对局/资料/我的”成为四个独立主页面，主要页面保持可预测导航；对局不是临时弹层。头像裁切和确认框仍可使用专用弹层。
3. 三步依次为“板子与规则 → 参与与座位 → 确认开局”。前两步不创建真实局，后退保留草稿。
4. 最终提交冻结 profileId、owner 展示快照、板子、参与模式、试玩/真实、座位和模型配置状态，并设提交锁。不要在 await 创建结果后再次读取可变化的当前档案作为 owner。
5. 新草稿默认试玩；旧草稿保持原模式。“玩家/观战”和“试玩/真实”是两个维度，不能混用 mode 枚举。
6. 丢失建局响应时先查询确认，不盲目重新创建；缺 Key 显示修复入口，不暗中降级试玩。

先交可运行的静态布局样稿和真实尺寸截图，视觉通过后接线；不能只给设计描述、元素数量或 DOM 存在断言。

### 3.3 M4 局中精修边界

- 宽屏保持发言阅读区为主体，右侧笔记约 320px；低于 960px 时玩家和笔记改抽屉，按原计划验证，不继续仅在 900px 把三栏堆成超长页。
- 保留“系统公开身份 / 玩家自称 / 我的推测”三层，不把推测绘制成系统真相。
- 复用现有 annotations-model、owner 绑定、草稿与冲突合并，不重写已验过的数据路径。
- 完成一整局的实际发言、技能、投票、结算后，再讨论新玩法。
