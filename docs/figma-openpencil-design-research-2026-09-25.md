## 2. Figma 教育版和 MCP：已经确认什么

### 2.1 教育认证与团队权限要分开看

教育认证通过后，仍需确认文件所属团队已使用 Education 计划，而非仍在另一个 Starter 团队。不能仅凭账户带教育认证就认定所有文件都享有相同功能。[Figma 教育版说明](https://help.figma.com/hc/en-us/articles/360041061214-Figma-for-Education)

官方当前列出的 Education MCP 读取额度为每天最多 200 次、每分钟 10 次；不是每月 200 次。部分写工具不计入该读取限额。MCP 次数、Figma AI 点数、外部模型用量是不同概念，不应混算。实际账户和团队席位由连接后的 `whoami` 核实。[额度与访问权限](https://developers.figma.com/docs/figma-mcp-server/rate-limits-access/)

### 2.2 不是“只能读设计稿”的旧版 MCP

目前官方提供原生画布写入：创建和调整 frame、组件、变体、变量与自动布局。专门的 Write to canvas 文档要求 Full 席位和目标文件编辑权限；不能把 Dev 席位默认当作完整写入席位。[原生画布写入](https://developers.figma.com/docs/figma-mcp-server/write-to-canvas/)

另有 Code to canvas，可将运行中的网页转成可编辑设计图层。该流程与原生写入的权限说明不同，官方允许任意席位在草稿范围使用部分能力。因此应分别验证“创建文件”“网页捕获”“原生编辑”，不能用其中一项成功推断全部可用。[网页转画布](https://developers.figma.com/docs/figma-mcp-server/code-to-canvas/)

注意官方表述尚不完全一致：综合帮助页与专门写入文档对 Dev 席位范围有差异；专门写入页仍列图像和自定义字体限制，工具目录则已列 `upload_assets` 等能力；实际安装的连接器又比网页工具目录多列 SVG 上传支持。采用保守规则：以实际返回的工具、文件权限及小样本结果为准，图像/字体单独验证，不承诺全自动无损。[综合帮助](https://help.figma.com/hc/en-us/articles/39216419318551-Get-started-with-the-Figma-MCP-server)

### 2.3 接入选择与工具用途

优先官方远程 MCP：`https://mcp.figma.com/mcp`，经账户授权使用。桌面 MCP：`http://127.0.0.1:3845/mcp`，适合读取桌面选区，但不是远程写工具的等价替代。若同时配置两者，需要区分服务名，避免调用落到缺少写能力的桌面服务。[远程设置](https://developers.figma.com/docs/figma-mcp-server/remote-server-installation/)

| 任务 | 连接后优先验证的能力 | 项目用途 |
| --- | --- | --- |
| 确认账号与计划 | `whoami` | 确认教育团队及席位，不记录令牌 |
| 建正式设计文件 | `create_new_file` | 创建 Design 文件，保存真实返回的 URL |
| 捕获现有页面 | `generate_figma_design` | 建立改版前基线，使用脱敏演示数据 |
| 整理规范和组件 | `use_figma` | 变量、自动布局、可编辑组件和状态 |
| 读取施工信息 | `get_design_context`、`get_variable_defs` | 获取布局和样式，不凭截图猜尺寸 |
| 对照外观 | `get_screenshot` | 对照实际实现截图 |
| 获取原始素材 | `download_assets` | 区分原图与重新渲染的截图 |
| 放入素材 | `upload_assets` | 实际连接器支持 PNG/JPG/GIF/WebP/SVG，单个不超过 10MB；SVG 作为矢量树导入，仍需试验复杂蒙版与滤镜 |

当前会话已连接，文件创建和原生页面写入已实测；其余工具不因出现在列表就视为项目验收通过。输出可以要求原生 HTML/CSS，不必接受默认的 React/Tailwind 结构。网页工具目录与实际连接器参数存在时差，调用时使用实际参数定义。[工具目录](https://developers.figma.com/docs/figma-mcp-server/tools-and-prompts/)

ZCode 是否能直接接入官方远程服务需要另外确认，不能由“支持 MCP”推断必然兼容。即使不能，施工方仍可使用我提供的节点链接、截图、变量表、原始素材和行为规格。

## 3. OpenPencil：值得试，但不应变成发布依赖

核对的项目是 **ZSeven-W/openpencil**，官网为 `op.zseven.tech`。不能混用同名项目的配置说明。当前仓库已转向 Rust 原生实现，截图时代的旧教程未必适用。[官方仓库](https://github.com/ZSeven-W/openpencil)

本次查询发布列表显示最新条目为 v0.8.4，标记为预发布；建议试点锁定具体版本，不把预发布工具更新自动带入游戏构建链。[发布记录](https://github.com/ZSeven-W/openpencil/releases)

适合它的工作是：让 AI 在可编辑画布上快速尝试两三种版式，进行骨架、内容、细节分阶段调整，并把本地设计文件纳入版本管理。它不是把一句“高级、精美”自动变成成品审美的保证。

官方 CLI 明确列出 `.fig` 导入、SVG/HTML 导入、设计变量和组件相关命令，例如：

```text
op import:figma input.fig --out output.op
```

这是资料中的命令示例，本轮没有执行。未找到可据此承诺 `.op → .fig` 原生、完整、无损往返的依据；正式设计和试验稿不能依赖未验证的反向同步。[官方 CLI 用法](https://raw.githubusercontent.com/ZSeven-W/openpencil/main/crates/op-cli/src/usage.txt)

v0.8.2 发布说明集中改进了 Figma 导入的蒙版、混合模式、组件覆盖、文字与矢量处理。这恰好说明复杂卡框和中文排版需要专门复验，而不是拿简单表单演示推断游戏素材百分百还原。[导入能力与改进](https://github.com/ZSeven-W/openpencil/releases/tag/v0.8.2)

## 4. 三方分工和交接边界

| 工作对象 | 正式依据 | 允许的试验 | 禁止的做法 |
| --- | --- | --- | --- |
| 页面布局与组件状态 | 经确认的 Figma 页面/组件 | OpenPencil 新建试验副本 | 同时改两份主稿却不注明版本 |
| 狼徽与已批准牌框 | 仓库的原始 SVG/PNG | 在画布中组合、缩放、对照 | 用截图、自动描摹或重导出覆盖已确认源文件 |
| 交互和数据行为 | 既有业务契约与测试 | 脱敏样例和原型演示 | 因设计工具方便而改档案归属或身份可见性 |
| 最终可用性 | 运行中的双端软件 | Figma 原型用于提前评审 | 只交效果图，声称键盘、离线、恢复均通过 |

具体顺序：现状页面取样 → Figma 建规范与正式稿 → OpenPencil 做有限布局变体 → 确认方案回到 Figma → 施工方改现有前端 → 相同状态截图复核 → 交互和制品验收。

Figma 中尽量使用语义命名、组件实例和自动布局；这比把页面画成大量无名矩形更容易稳定交付。[官方文件组织建议](https://developers.figma.com/docs/figma-mcp-server/structure-figma-file/)

## 5. 我们应该做出怎样的页面

以下是项目设计建议，不是工具官方效果承诺。

### 5.1 视觉命题：月夜议会，而非后台管理面板

延续暗黑哥特、精细金属雕刻的基调。大厅以狼徽与开局动作为焦点；对局以人物、发言和判断为焦点。装饰主要集中在徽记、牌框、关键分隔和主按钮，长文本区保持干净，不能每个输入框都套复杂金边。

建议首轮比较的六个基础色：

| 名称 | 建议值 | 用途 |
| --- | --- | --- |
| 夜墨 | `#0D1018` | 大面积底色 |
| 石板 | `#191F2A` | 面板和层级 |
| 月银 | `#C6D0DB` | 主文字、细节高光 |
| 古金 | `#B69A60` | 品牌与主要动作 |
| 暗绯 | `#9C4654` | 危险、强调，不替代文字状态 |
| 雾灰 | `#8E99AA` | 次级说明，必须实际测对比度 |

颜色是待验证的起点，不是直接全局替换清单。身份阵营保留现有语义；未知身份不能因颜色或边框泄露真实身份。选中、发言中、死亡、断线等状态需要图形/文字共同表达。

字体角色建议：标题试用有克制感的中文宋体/衬线；正文用清晰中文黑体；座位号与倒计时用稳定的等宽数字。先确认实际可用字体与许可证，无法在 Figma MCP 加载时明确标记替代字体，不把替代排版视为最终测量。正文不使用装饰性哥特字体。

### 5.2 首批三类页面，而不是立即全站重画

| 页面 | 手机端重点 | 电脑端重点 | 能明显改善观感的要点 |
| --- | --- | --- | --- |
| 游戏大厅 | 首屏看清当前玩家、继续对局/新开局；高级配置后置 | 狼徽主视觉与清晰任务区；不堆满表单 | 一个明确视觉中心，统一留白与按钮层级 |
| 玩家中心 | 自定义头像、更换/裁切/失败提示；档案切换易理解 | 头像与档案内容分区，局记录有清楚空态 | 像玩家身份页，而非数据库编辑页 |
| 对局页面 | 读发言、选目标、确认动作优先；笔记不压缩主内容 | 座位区、发言时间线、笔记侧栏协调 | 牌框有质感，发言有层次，关键信息不过度闪动 |

账号继续采用已确定的“仅本机多个玩家档案”，不添加密码、注册或云同步。玩家头像必须允许自定义，并保留默认头像回退。当前所选档案与本局归属是两个概念，页面要明确展示，不能借改版合并。

对局三层标注沿用自称、候选、备注的语义；避免把私人推测画成公开确认身份。候选冲突、草稿未保存、迁移待确认、断线恢复均要设计状态，不只设计正常空白页。

### 5.3 卡框与背景资产策略

复用 `design/brand/v2/wolf-emblem.svg` 和 `design/card-frames/v3/assets/` 内已确认的素材。小卡保持薄边、清晰头像窗口、少量角饰；大卡才承载更丰富的纹理。保持现有 112px compact 分界的视觉测试，不能一张复杂大卡框机械缩到所有尺寸。

若确实缺少大厅氛围背景或统一材质，可由我另行生成并提供成品；施工方无需具备生图能力。素材与文字、按钮、状态分离，不能把整个操作页面做成一张图。首轮先用现有品牌和牌框完成排版，确认缺口后再补图，不预先制造大量无用素材。

动态效果集中于一两个有意义的反馈，如当前发言座位强调或确认动作反馈；不全屏持续粒子、不让细金边一直发光。减少动态效果模式要有静态方案。

## 6. Figma 文件组织与首轮执行步骤

已建文件：**[AI 狼人杀 · 双端界面设计](https://www.figma.com/design/eOztPb6PdYZRhhx6YAcQKX)**，位于当前唯一教育团队的草稿。未调整公开分享权限。后续继续使用该文件，不重复创建。

已创建的页面分区（目前是空分区，尚非页面设计成品）：

```text
00 · 使用说明与现状参考
01 · 视觉规范
02 · 组件与状态
03 · 手机端
04 · 电脑端
05 · 交互与验收
90 · 探索与备选（不施工）
```

### 阶段 A：接通与最小验证

1. 已完成：用户安装并授权 Figma，不需要发送密码或 API Key。
2. 已完成：核实账号、教育团队、席位和实际工具列表。
3. 已完成：创建文件、读取结构、初始化七个页面；后续修改继续沿用真实 URL。
4. 在测试区创建一个自动布局按钮、一个带中文的卡片组件和一个变量；修改尺寸后读回并查看截图。
5. 分别试验 SVG、金属位图和中文字体；不支持的能力记录清楚，并选择保留原始素材的导入路径。

完成标准：文件可打开；元素可编辑而非整页图片；变量和组件有效；字体或图片限制有记录。仅能读文件不算写入验证通过。

### 阶段 B：基线和组件

1. 取当前桌面和手机界面作基线，用 Mock/固定演示数据，不上传真实个人头像、私人笔记或设置密钥。
2. 先建颜色、间距、文字、触区等规范，再建按钮、玩家头像、座位卡、状态标签、档案选择器、笔记行、对话框等组件。
3. 记录组件到既有前端函数/样式的对应表；不把 Code Connect 或新的前端框架作为先决条件。

完成标准：相同控件有一致状态和命名；危险动作、不可用状态、焦点、载入、失败均可检查。每个组件能说明在现有代码何处落地。

### 阶段 C：三页面双端正式稿

先完成 390×844 手机稿和 1440×900 桌面稿，共六个主画面；再补 320×568 小屏、约 960px 过渡宽度和大字号压力状态。记录断点依据，不把桌面三栏等比压进手机。

对大厅、玩家中心先确认整体美术和信息层级；对局页随后用长昵称、长发言、满候选、空态、断线等真实负载验证。每轮只提交两个有明确差异的方案供选择，避免大量近似稿稀释判断。

完成标准：用户确认方向；重要状态完整；主操作不用寻找；屏幕缩小时文字、头像与触区不会互相挤压。

### 阶段 D：OpenPencil 小范围试点（可选，不阻塞 Figma）

只选一个包含中文、头像、金属牌框、长文本和自动布局的组件集合及一个页面，导出 `.fig` 副本后导入锁定版本的 OpenPencil。比较图像、图层可编辑性、文字换行、组件覆盖和缩放；通过后再做大厅布局 A/B 探索。

完成标准：有原稿、导入稿与偏差记录；没有无法接受的失真才扩大使用。失败时保留 Figma 正式流程，不要求施工方为工具兼容性重写游戏。

### 阶段 E：施工交接与验收

交付包至少包含：已批准节点链接、双端截图、变量表、组件状态表、原始素材索引、交互规则、断点说明、尚未批准的内容清单。截图必须标尺寸与数据状态。

施工按一个页面一个验收单推进，继续使用现有 HTML/CSS/JavaScript。设计工具输出只是参考，不得覆盖业务状态管理、档案归属、恢复令牌或私人标注隔离逻辑。

## 7. 首轮验收表

账号、创建文件、原生页面创建已通过基础验证；其余项目待执行，不能把基础连接成功等同于整体设计验收通过。

| 检查 | 必须看到的证据 |
| --- | --- |
| 教育权限 | 目标文件的实际团队与席位，创建/编辑各自的执行结果 |
| 结构质量 | 组件、变量、自动布局可编辑，非整页贴图 |
| 资产忠实度 | 狼徽、卡框、纹理在不同尺寸无裁切、变形或明显模糊 |
| 中文排版 | 长昵称与多行发言的实际渲染，替代字体有显式记录 |
| 触控 | 手机主操作建议至少 48px 触区；不得因视觉收窄削弱已有 52px 控件 |
| 响应式 | 320/390/960/1440 宽度下无关键内容遮挡、横向意外溢出 |
| 输入可用性 | 键盘打开、长备注、未保存关闭、焦点与 Esc 的实际交互 |
| 身份语义 | 自称/推测/公开信息分明，未知阵营不泄露，本局归属不混淆 |
| 异常状态 | 无档案、无头像、图片失败、断线、恢复、导入失败可理解并能操作 |
| 实装一致性 | 相同演示状态下 Figma/浏览器截图并排检查；偏差逐项关闭 |
| 软件稳定性 | 按改动范围运行既有门禁；最终制品核对不以设计稿代替 |

## 8. 给施工 AI 的约束摘要

> 本轮是既有狼人杀产品的视觉与交互升级，不是框架迁移。正式设计以批准的 Figma 节点为准，OpenPencil 仅作备选探索。沿用本地多档案和玩家自定义头像，严格区分当前档案与对局归属。复用已批准的狼徽与 V3 牌框，不把效果图当生产资产，不修改隐藏身份的信息边界。先接通设计读取并列出无法还原的项目；每次只实现一个页面或组件集合，提交双端相同状态截图、交互证据和回归结果。没有生图能力时列清素材用途、尺寸、透明要求，由设计方提供；不得用 emoji 或随意网络图片代替批准素材。
