## 1. 施工目标与完成定义

本轮整改完成后，项目必须同时满足以下条件：

1. 默认只监听本机回环地址，局域网访问必须显式开启并经过配对认证。
2. 配置、对局列表、令牌等管理接口不能被未授权客户端读取或修改。
3. 外部输入和模型输出不得以未转义 HTML 进入页面。
4. 畸形 URL、存盘失败、正常对局结束等场景不能造成进程退出、状态卡死或数据无法重试。
5. 丘比特链人等动态阵营在胜负、评分、复盘和提示词中使用同一套权威判定。
6. 移动端复盘能可靠从“生成中”进入“完成”或“失败”，不依赖未授权请求。
7. 读档后保留当前配置的 LLM 并发语义，同时不破坏决策日志的可重放性。
8. 自动化测试、覆盖率、依赖审计、桌面端和 Android 构建检查全部达到本文门槛。
9. 施工方提交变更说明、测试证据、升级说明、回滚说明和剩余风险清单。

完成不是“代码已写完”，而是本文所有 P0/P1 验收项通过、P2 项完成或有书面延期决定，并且发布候选包通过完整冒烟测试。

## 3. 总体技术决策

### 3.1 网络暴露策略

采用“本机默认安全、局域网显式开启”的双模式：

- 默认模式：监听 `127.0.0.1`，保持现有单机 Web、Electron 和本地 Android 调试流程可用。
- 局域网模式：只有显式设置 `WW_LAN=1` 时才监听 `0.0.0.0`；启动日志必须醒目标明局域网已开放。
- 可选覆盖：支持 `WW_HOST`，但生产发布说明必须强调开放地址的风险。
- 禁止为了兼容而恢复无条件 `0.0.0.0` 监听。

### 3.2 认证模型

使用两层能力边界：

1. **管理会话**：用于读取/修改配置、列出全部对局、读取对局令牌、创建新对局和访问管理统计。
2. **对局能力令牌**：继续使用现有玩家令牌/上帝令牌访问单局资源，避免大规模重写游戏协议。

建议实现：

- 回环地址访问可由服务端自动建立本机管理会话。
- 局域网首次访问显示一次性 6–8 位配对码；配对码有过期时间、失败次数限制和生成频率限制。
- 配对成功后签发高熵随机会话 ID，通过 `HttpOnly; SameSite=Strict` Cookie 保存；仅在 HTTPS 环境设置 `Secure`。
- 服务端仅保存会话摘要或使用带服务端密钥的完整性签名，不在 URL 中传递管理凭证。
- 状态改变接口校验 `Origin`/`Host`；不启用宽泛 CORS。
- 所有认证失败统一返回 401/403，不泄露资源是否存在及敏感字段。

### 3.3 生命周期状态

把布尔组合收敛为显式状态：

```text
created -> running -> paused -> running -> finished
                    \-> error
```

如果暂不重构为枚举，也必须用单一状态转换函数维护 `running`、`paused`、`finished` 的互斥关系。禁止在多个分支中零散写布尔值。

### 3.4 阵营语义

明确两个不同概念：

- `factionOf(player)`：最终胜负阵营，只返回 `good | wolf`，用于胜负、评分、复盘归属、经验总结。
- `categoryOf(player)`：角色类别，返回 `wolf | god | villager`，用于角色规则、神民区分和特定技能。

丘比特链人后的动态归属必须由游戏实例计算，不能从 `ROLES[role].team` 静态读取。狼人夜聊、预言家查验、骑士决斗等具体规则仍按规则定义执行，不得机械替换为最终阵营。

## 阶段 1：网络边界与接口认证

**预计：2–2.5 人日**

### 1.1 监听地址

- 在 `server.js` 中引入明确的 host 解析逻辑。
- 默认 `127.0.0.1`；仅 `WW_LAN=1` 时默认改为 `0.0.0.0`。
- 启动日志打印实际监听地址、端口和访问模式，不打印密钥或会话 ID。
- Electron 内嵌服务显式传入回环地址，不依赖环境变量碰巧正确。

### 1.2 管理会话和配对

新增小型认证模块，建议放置于 `src/auth.js` 或 `src/auth/`：

- 安全随机生成会话和配对码。
- 支持过期、吊销、最大会话数、失败计数和恒定时间比较。
- API 提供配对状态、提交配对码、退出会话三个最小端点。
- 不把 LLM API Key、玩家令牌、上帝令牌写入日志或错误消息。

### 1.3 接口权限矩阵

施工方应先建立集中式路由权限表或中间件，禁止在处理器内部临时散落判断。

| 资源 | 未认证 | 管理会话 | 玩家令牌 | 上帝令牌 |
|---|---:|---:|---:|---:|
| 静态页面/资源 | 允许 | 允许 | 允许 | 允许 |
| 健康检查、非敏感版本信息 | 允许 | 允许 | 允许 | 允许 |
| 配对状态/提交配对码 | 有条件允许 | 允许 | 无额外权限 | 无额外权限 |
| 读取/修改 LLM 配置 | 拒绝 | 允许 | 拒绝 | 拒绝 |
| 测试/探测 LLM 配置 | 拒绝 | 允许 | 拒绝 | 拒绝 |
| 创建对局 | 拒绝 | 允许 | 拒绝 | 拒绝 |
| 列出全部对局 | 拒绝 | 允许 | 拒绝 | 拒绝 |
| 获取一局全部令牌 | 拒绝 | 允许 | 拒绝 | 拒绝 |
| 单局玩家视角 | 拒绝 | 允许 | 本人范围 | 允许 |
| 单局上帝视角/管理操作 | 拒绝 | 允许 | 拒绝 | 允许 |

### 1.4 URL 与请求防护

- 把路径解码移入受控异常处理；URI 解码失败返回 400。
- 对请求体设置明确大小上限，超限返回 413。
- 只接受声明支持的 `Content-Type`。
- 对方法、路径和 JSON 解析错误返回稳定的 JSON 错误结构。
- 配置测试接口必须阻止凭证被任意 `baseUrl` 外带：修改地址时要求重新输入 API Key，或只允许向已保存并经用户确认的目标发送凭证。
- 对配对、登录、配置测试和创建游戏增加轻量限流。

### 阶段 1 验收

- 默认启动后，其他局域网设备无法建立连接。
- 局域网模式下，未配对客户端无法读取配置、列出游戏、取令牌、创建游戏或触发模型请求。
- 修改 `baseUrl` 时不能静默沿用旧 API Key 向新域名发请求。
- 畸形 URL、超大请求体、坏 JSON 均只影响该请求。
- 现有 Electron 本地启动、浏览器本地访问、玩家/上帝单局流程仍可工作。

## 阶段 2：前端 XSS 与 Electron 加固

**预计：1–1.5 人日**

### 2.1 DOM 渲染边界

- 将现有通用元素创建函数拆为安全的 `elText(...)` 与受控的 `elHtml(...)`。
- 玩家名、模型输出、复盘内容、系统消息、错误信息、URL 参数、存档内容一律使用 `textContent`。
- 只允许代码内常量模板进入 `innerHTML`。
- 若确有富文本需求，应先定义严格白名单并使用成熟净化库；本轮默认不引入富文本。
- `sanitizeInline` 只用于提示词/格式清理，不能被当成 HTML 安全函数。
- 检索并审计所有 `innerHTML`、`insertAdjacentHTML`、事件属性和字符串拼接 URL。

### 2.2 浏览器安全策略

- 为 Web 页面增加与实际资源相容的 CSP，至少约束 `default-src`、`script-src`、`style-src`、`img-src`、`connect-src`、`object-src` 和 `base-uri`。
- 禁止内联脚本后再收紧 CSP；若暂时存在内联样式，应记录迁移债务而不是使用过宽通配符。
- 增加 `X-Content-Type-Options: nosniff`、合理的 `Referrer-Policy` 和 `frame-ancestors` 等响应头。

### 2.3 Electron

- 使用 `new URL(target)` 后进行协议、hostname、port 的精确比较，不再使用 `includes`。
- 明确开启 `contextIsolation: true`、`sandbox: true`，关闭 `nodeIntegration`。
- 拒绝非必要的权限请求和新窗口；外链只交给系统浏览器打开。
- 导航白名单只允许当前内嵌服务的精确 origin。

### 阶段 2 验收

- 以下载荷在桌面和移动页面中均只显示为普通文本，不执行：`<svg/onload=alert(1)>`、带引号事件属性、闭合标签脚本、恶意玩家名。
- Electron 无法导航到相似 hostname、用户名嵌入 URL 或不同端口的地址。
- 开发者工具中无 CSP 误拦截核心功能，也无明显宽泛白名单。

## 阶段 3：对局生命周期与可靠存盘

**预计：1–1.5 人日**

### 3.1 状态转换

- 引入 `created/running/paused/finished/error` 状态或等价的集中转换函数。
- `_drive` 正常返回、异常、暂停、恢复和结束都必须在 `finally`/统一收口处更新状态。
- 正常结束必须设置 `running = false` 和 `finished = true`。
- `startGame` 同时检查是否已经开始、是否已结束和当前状态，不能仅用 `running` 阻止重复启动。
- 清理任务依据明确状态和最后活动时间执行；运行中和仍有活跃连接的游戏不能误删。

### 3.2 原子存盘与重试

- 临时文件写入并成功重命名后，才更新 `savedStamp`。
- 保存失败时保持 dirty 状态，返回失败或抛出受控错误，不得假装成功。
- 增加有上限的指数退避重试，并记录不含敏感内容的结构化错误。
- `saveActive()` 返回 `Promise`，汇总各局保存结果。
- SIGINT/SIGTERM 优雅退出：停止接收新请求，等待活动写盘完成，设定合理总超时后退出。
- 保存数据增加 `schemaVersion`；读档对旧版本执行显式迁移或兼容读取。

### 3.3 崩溃一致性

- 同目录创建临时文件，避免跨文件系统重命名问题。
- 启动时识别残留临时文件，但不得自动覆盖较新的有效存档。
- 写盘日志包含游戏 ID、结果和耗时，不包含对局秘密、令牌或 API Key。

### 阶段 3 验收

- 完成局可被清理，不能再次启动。
- 模拟首次写盘失败、第二次成功时，第二次确实重新执行写盘。
- 在写盘期间发送 SIGTERM，进程在超时内完成保存后退出。
- 旧版存档夹具能够载入；新版存档包含版本号。
- 临时文件/重命名失败不破坏上一份有效存档。

## 阶段 4：统一动态阵营判定

**预计：1 人日**

### 4.1 权威 API

- 在 `Game` 或独立规则模块中提供 `factionOf(player)` 和 `categoryOf(player)`。
- 逐处审查 `ROLES[p.role].team`、`teamOf()` 和硬编码 `god`/`good` 判断。
- 胜负、评分、复盘、经验总结和相关提示词统一使用最终阵营。
- 身份展示、技能限制、狼人频道、查验结果等使用角色类别或对应规则函数。

### 4.2 必测矩阵

| 场景 | 预期最终阵营 | 角色类别保持 |
|---|---|---|
| 普通狼人 | wolf | wolf |
| 普通神职 | good | god |
| 普通村民 | good | villager |
| 丘比特链人归狼 | wolf | 原角色类别 |
| 丘比特链人归好 | good | 原角色类别 |

测试至少覆盖链到狼人、神职和村民三种情况，并验证：胜负归属、胜利加分、复盘中文阵营名、经验总结提示词四者一致。

### 阶段 4 验收

- 动态归狼玩家获狼方胜负和评分，不再被静态标记为好人。
- 神职复盘正确显示“神职”或产品约定文案，不再误标成普通村民。
- 原有狼人夜聊、预言家查验和技能规则没有因阵营重构发生语义漂移。

## 阶段 5：修复移动端复盘并抽取共享逻辑

**预计：1–1.5 人日**

### 5.1 复盘状态机

推荐复用现有 SSE：

1. 携带有效能力令牌 POST 创建复盘任务。
2. 收到 202 后显示生成状态和可取消的 UI。
3. 监听同一局的 SSE 复盘状态事件。
4. `done` 时使用安全文本渲染结果；`error` 时显示可重试提示。
5. SSE 断开时使用携带同一令牌的有限次数轮询兜底，并设置退避和总超时。

禁止 POST 后立即进行无令牌 GET；禁止依赖刷新页面才能看到完成结果。

### 5.2 共享前端模块

逐步抽取桌面 Web 和移动端重复逻辑，建议模块：

- `api-client`：认证、令牌、统一错误、超时。
- `view-stream`：SSE 连接、重连、降级轮询。
- `review-controller`：复盘状态机。
- `dom`：安全文本节点与受控静态模板。

本阶段只抽取与整改直接相关的重复代码，不进行全量前端重写。

### 阶段 5 验收

- 移动端发起复盘后，无需刷新即可看到完成结果或明确错误。
- SSE 临时断开后能够重连或经认证轮询恢复。
- 同一复盘操作不会因重复点击创建大量并发任务。
- 桌面端和移动端对认证失效、网络超时、生成失败给出一致的可理解提示。

## 阶段 6：读档执行配置与决策日志稳定性

**预计：0.5–1 人日**

- `Game.fromJSON` 接收当前运行配置中的 `parallelLlm`，或恢复后由 API 层统一注入。
- 存档保存游戏语义数据，不固化不应跨环境继承的运行时资源和密钥。
- 明确恢复策略：本计划采用“读档后使用当前服务器配置”，并在日志中记录配置差异。
- 验证串行/并行调度只影响可并行的模型调用，不改变白天发言等必须串行的游戏语义。
- 对相同存档和决策日志回放，验证随机决策、阶段推进和最终事件序列稳定。

### 阶段 6 验收

- `parallelLlm=true/false` 两种当前配置下读档均按当前值运行。
- 恢复后不会重复已落盘决策，也不会跳过待执行决策。
- 决策日志在允许的并发调度下保持确定性约束；若无法完全确定，差异范围必须被测试明确界定。

## 7. 风险与回滚

| 风险 | 预防/缓解 | 回滚方式 |
|---|---|---|
| 认证改造导致现有客户端 401 | 先统一 API 客户端；保留短期兼容日志，不保留匿名管理权限 | 回滚客户端与服务端同一组提交 |
| CSP 阻断现有内联资源 | 报告模式验证后收紧；清点全部资源来源 | 临时回退到已审查的较宽 CSP，不移除文本转义 |
| 生命周期重构影响恢复 | 状态转换表 + 旧存档夹具 | 回退状态枚举实现，保留结束复位补丁 |
| 阵营统一改变特殊规则 | 区分 faction/category，按规则逐条测试 | 回滚调用点，不回滚新增测试和语义文档 |
| Electron 跨主版本升级破坏打包 | 独立分支/提交，先构建再合并 | 回退依赖升级提交，保留应用层安全加固 |
| Android 工具链升级要求更高 SDK/JDK | 在干净构建环境预检版本要求 | 回退依赖和锁文件，记录未解决告警 |

严禁以关闭认证、恢复不安全 `innerHTML`、跳过存盘错误或禁用测试作为正式回滚方案。
